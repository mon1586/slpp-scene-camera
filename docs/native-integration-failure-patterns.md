# ネイティブ連携の失敗パターン

Sexlab Scene Camera POC で発生した問題から、別の機能追加でも再発しやすいものを抽象化して残す。個別バグの時系列ではなく、実装時と調査時の判断基準として使う。

## 1. ビルド成功とランタイム互換性は別物

CommonLibSSE-NG の `RELOCATION_ID` は `(SE, AE)` の順で指定する。IDの組が正しくても順序を逆にするとコンパイルとロードには成功し、該当処理を初めて通った時だけ別関数を呼んで CTD する。

- 生の数値を転記するときは、各値がどのランタイム用か名前付きで確認する。
- 利用中ランタイムで実際に解決された Address Library ID をクラッシュログで確認する。
- 参照元プラグインと同じ処理を使う場合は、関数シグネチャだけでなくランタイム別IDも一次ソースと照合する。
- コンパイル、DLLロード、対象コードパスのゲーム内実行を別々の検証段階として扱う。

今回の具体例では、AE 1.6.1170 でSE用ID `69271` が解決されていたことが決め手になった。正しい組は `RELOCATION_ID(69271, 70641)` である。

## 2. hook のインストール成功は、発火の証明ではない

vtableへの書き込み成功や「hook installed」というログは、対象関数がゲーム中に呼ばれたことを保証しない。型名や一般的な更新経路から選んだ hook が、実際のランタイムや他Modの構成では使われない場合がある。

- hook thunk の初回実行時に一度だけログを出し、スレッドIDも記録する。
- インストール、初回発火、毎フレーム処理の到達を別の観測点にする。
- 発火しない場合は待ち時間を増やすのではなく、実際にカメラを更新しているプラグインの hook 経路をソースから追う。

このPOCでは `PlayerCamera::Update` のhookはインストールできても発火せず、SmoothCamが利用する `TESCameraState::Update` が実際の統合点だった。

## 3. 他Modがvtableを差し替える場合、hookする対象と順序が変わる

別のSKSEプラグインがvtableを複製・差し替えていると、静的な元vtableだけをhookしてもそのプラグインの実行経路には入れない。また、先にhookすると後から差し替えられて消えることがある。

- 依存先の初期化後に、実際のインスタンスが現在参照しているvtableをhookする。
- 同じvtableを共有する状態を重複して書き換えない。
- thunkでは既存のoriginalを先に呼び、依存先が確定した出力の後に自分の変更を適用する。
- hook順序は暗黙の前提にせず、architectureとログに残す。

## 4. 呼び出しスレッドの制約を利用側で推測しない

イベントを受け取ったスレッドと、ゲーム状態を安全に変更できる更新コンテキストは一致するとは限らない。一方で、外部APIに存在しないスレッド制約を利用側で追加すると、正当な呼び出しまで拒否する。

- 外部APIの制約は公開契約と実装で確認し、利用側独自の先行拒否を設けない。
- APIの戻り値をそのまま判定・記録する。
- イベントsinkでは識別情報だけを固定長mailboxへ保存する。
- カメラ所有権の変更とNiNode操作は、実際に発火が確認できたカメラ更新コンテキストで行う。

## 5. API資料と配布中実装の両方を観測する

公開APIに記載されたイベントと、互換目的で実装が追加送信しているイベントは一致しないことがある。引数が `strArg` と `numArg` のどちらへ載るかも、呼び出し形式で変わる。

- 最初のPOCではイベント名、sender、文字列引数、数値引数を加工前にログへ出す。
- 公開APIを基準にしつつ、実際に導入されているバージョンの送信側ソースも確認する。
- 差異はController側のadapterで吸収し、Coreへ持ち込まない。
- ネイティブイベントだけで必要情報を取得できるなら、Papyrus bridgeを先に追加しない。

## 6. 検証は到達点ごとに区切る

ネイティブ連携は一度に成否を判断せず、次の順でログと実機挙動を確認する。

1. DLLが対象ランタイムでロードされる。
2. 外部イベントを受信し、payloadを正しく解釈できる。
3. 更新hookが実際に発火する。
4. 外部カメラAPIの所有権取得に成功する。
5. 独自poseが画面へ反映される。
6. 終了イベントで元の所有者へ制御を返す。

後段で失敗したときに前段まで疑い直さず、最後に成功した観測点から調査を始める。クラッシュした場合は、クラッシュスタック上の最初の自作DLLフレームと、その直前に解決されたAddress Library IDを優先する。
