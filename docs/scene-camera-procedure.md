# シーンカメラ手続き

状態: **有効候補のA/D切り替えまで実装／ゲーム内確認待ち**

## 目的

Runtimeから受け取るシーンの開始・更新・終了を一つの手続きとして扱い、必要なCore機能を順番に呼び出す。個々の計算方法とゲーム固有の入出力はこの手続きに持ち込まない。

## 基本フロー

```text
Runtimeからシーン開始通知を受け取る
  -> Runtimeへ参加者情報を要求する
  -> 対象シーンなら開始状態を保持する

Runtimeからアニメーション開始通知を受け取る
  -> 次の更新でアンカーを取得するよう予約する

Runtimeからアニメーション変更通知を受け取る
  -> アンカー追従を維持したまま指定秒数後の候補再評価を予約する
  -> 待機中に同じ通知を受けた場合は遅延を数え直す

Runtimeから更新通知を受け取る
  -> Runtimeへ現在のプレイヤー身体中心と向きを要求する
  -> Coreのアンカー計算を呼び出す
  -> 成功したアンカーで保持値を更新する
  -> debug可視化が有効ならRuntimeへアンカー表示を要求する
  -> 初回または予約済みの更新なら後続のCore機能を順番に呼び出す
  -> 出力が得られた場合だけRuntimeへ反映を要求する

Runtimeから継続更新を受け取る
  -> 現在のアンカーから選択中の構図を再生成する
  -> デバッグモード中はcamera制御を取得せず、切り替え入力を前後のデバッグ対象へ反映する
  -> 通常モードでは切り替え入力があれば前後の有効候補へカットする
  -> 通常モードで出力が得られた場合だけRuntimeへ反映を要求する

プリセットEditorを終了する
  -> 編集していたプリセットを含めて候補を再評価する
  -> 編集していた保存済みプリセットが候補に存在すれば可視状態にかかわらず選択を維持する
  -> 引き継げる編集対象がなければ編集前の選択へ戻す。編集前の選択もなければ通常cameraへ戻る
  -> 選択結果を通常のscene cameraへ反映する

Runtimeからシーン終了通知を受け取る
  -> 現在処理中のシーンと一致するか確認する
  -> 保持している結果と状態を破棄する
  -> Runtimeへ必要な終了処理を伝える
  -> 待機状態へ戻る
```

Runtimeは通知と入出力を担当し、手続き上の判断は行わない。Coreは呼び出された機能だけを計算し、前後の処理順序を知らない。

## シーン通知の採否

有効な入力について、次の規則を適用する。同じscene keyが別のシーンで再利用された場合の古い通知は、この一致判定だけでは区別できない。同一key再利用後の旧通知を排除する保証は現在持たない。一致しない終了と、ロード前に受理済みの保留通知は除外する。

| 現在の状態 | 通知 | 期待する動作 |
| --- | --- | --- |
| 対象なし | プレイヤー参加のAnimationStarting | 開始準備へ進み、参加者を保持する |
| 対象なし | プレイヤー参加のAnimationStart | Startingを省略した開始として受理し、初回評価を予約する |
| 開始準備 | 同一keyのAnimationStarting | 開始準備を維持し、その通知の参加者情報へ更新する |
| 開始準備 | 同一keyのAnimationStart、プレイヤー参加あり | activeになり、初回評価を予約する。参加者はStart時点の情報へ更新する |
| 開始準備 | 同一keyのAnimationStart、プレイヤー参加なし | 開始準備を破棄し、対象なしへ戻る |
| 開始準備またはactive | 別keyの開始通知 | 現在の対象を置き換えず無視する |
| active | 同一keyのAnimationStartingまたはAnimationStart | 重複として無視し、参加者・初回評価・開始時刻を更新しない |
| 対象なしまたは開始準備 | AnimationChange | 無視する |
| active | 同一keyのAnimationChange | 初期アンカー未取得でも受理し、最後の通知から1秒後へ評価期限を更新する |
| active | 別keyのAnimationChange | 無視する |
| 開始準備またはactive | 同一keyのAnimationEndingまたはAnimationEnd | 対象を終了する。どちらの通知だけでも終了できる |
| すべて | 一致しない終了通知 | 現在の対象へ影響させない |

プレイヤー不参加のAnimationStartingは受理しない。AnimationStartでの不参加は、上表の「開始準備中の同一key」の場合だけ準備の取消として扱う。終了後の重複終了通知は一致する対象がないため何も終了しない。

## アンカーの更新境界

- シーン開始時は、有効なプレイヤー身体中心を取得できるまでカメラ制御を取得せず、更新ごとに再試行する。取得できた最初の更新でアンカーを生成する。
- active scene中は更新ごとに身体中心を取得し、アンカーと選択中のカメラ構図を追従させる。
- 継続更新で身体中心を一時的に取得できない場合は、直前の有効なアンカーとカメラ構図を維持する。
- アニメーション変更時はアンカー追従を継続し、P+の`AnimationChange`通知から1秒経過した後の最初の更新で候補と可視性を再評価する。
- 同じscene keyの`AnimationChange`を再度受けた場合は再評価期限を更新する。
- ポーズ中は通常の追従と定期候補評価を行わない。変更待機の期限がポーズ中に経過した場合は、通常はポーズ解除後の最初の更新で再評価する。Editorの数値previewとデバッグ設定変更に必要な評価・解放・通常制御への復帰はポーズ中も処理する。取得再試行の上限と終了条件は[`debug.md`](debug.md)に従う。停止対象と例外の区分は[`runtime-spec.md`](runtime-spec.md)に従う。
- シーン終了時は破棄する。
- 通常・デバッグモードで0.5秒ごとにアンカーLOSを再評価し、A/Dの選択候補を更新する。現在の選択は使用不能でも維持し、自動切り替えしない。条件は[`clearance-design.md`](clearance-design.md)に従う。
- アニメーション変更後の再評価待ちでは、定期評価とA/D切り替えを止める。待機中のA/Dは後へ持ち越さない。再評価した更新で定期評価を重ねて実行せず、次の定期評価はその評価からポーズを除く0.5秒後とする。期限に入力が欠落していれば評価を保留し、有効な入力を取得できた更新で再開する。

P+の`AnimationChange`は変更開始時に送られ、変更後の姿勢を保証する完了通知ではない。1秒待機はこの制約に対する暫定方針であり、同期完了を保証するものではない。

## 失敗時の扱い

- 対象シーンでない開始通知は何も開始せず終了する。
- 最初の有効なプレイヤー身体中心または向きを取得できない間は、カメラ制御と候補評価を開始せず再試行する。
- 継続追従中に有効な身体中心または向きを一時的に取得できない場合は、直前の有効な結果を維持する。
- 身体入力の欠落、候補の使用不能、選択中の構図生成失敗は区別し、下表に従う。
- debug可視化に失敗した場合は警告だけを記録し、計算結果と手続きを維持する。
- 対応しないscene keyの終了通知は、現在の手続きへ影響させない。
- ロード、新規ゲーム、処理境界の異常、watchdogでは保持状態の破棄と復帰を要求する。解放に失敗した場合は終了済みとせず、復帰を再度処理できる機会へ持ち越す。
- 終了・resetの復帰待ちに入った時点で、候補評価、A/D、Debug復帰、旧シーンのpreviewを取り消し、編集をロックする。解放完了までは構図の反映・再取得・新しい開始や変更の受理を行わない。
- 復帰の再試行はポーズ中も許可する。解放完了後に受理した有効な開始だけで新しいシーンへ進み、処理済みのresetを遅れて再適用しない。
- 終了したシーンのpreview値とEditor終了後の復帰要求は次のシーンへ持ち越さない。Editor内の下書きは残してよいが、次のシーンで明示的にpreviewを開始し、再確認するまでは保存できない。
- カメラposeがまだ生成されていない段階では、カメラ制御を取得せず、アンカーをカメラ位置として直接出力しない。

### 失敗の種類と再開

| 失敗 | 現在の構図・シーン | 再開条件 |
| --- | --- | --- |
| 初期身体入力・向きが無効 | 取得と初期評価を保留、シーンは維持 | 入力復帰で初期評価。時間上限は継続 |
| 取得済み後の身体入力が無効 | 直前のアンカー・構図を維持、A/D停止 | 入力復帰後の再評価で切り替えを再開 |
| 候補の姿勢またはLOSが無効 | その候補を使用不能とする。可視性だけでは現在の選択を解除しない | 後の再評価で候補へ復帰可能 |
| 通常表示の選択構図を生成できない | 復帰し、対象シーンを破棄 | 改めて有効な開始通知が必要 |
| 編集値から構図を生成できない | エラーを表示し、最後の有効な構図を維持 | 有効な値のpreviewを確認して再開 |
| カメラ取得を拒否された | カメラを取得せず、対象シーンと選択は維持 | 別候補へのA/D、変更後評価、preview要求、Debug OFFなど次の適用契機で取得可能か確認 |
| カメラ表示失敗・所有権喪失 | 復帰し、対象シーンを破棄。編集はロック | 改めて有効な開始通知とpreview確認が必要 |
| 終了・resetの解放失敗 | 復帰待ちを維持し、旧シーンの操作・評価・反映を停止 | ポーズ中を含め、次に復帰を処理できる機会で再試行 |

取得拒否後に毎更新の無制限再取得は行わない。Debug OFFの明示的な復帰だけは[デバッグ仕様](debug.md)の試行間隔・回数・期限に従う。シーンを破棄した後は、A/DやDebug OFFだけでは対象シーンを作り直さない。

### シーン時間の上限

現在のwatchdogは、AnimationStartを受理してから実時間30分を超えた更新でシーンを終了する。30分ちょうどでは終了しない。変更通知や身体入力の取得成功で開始時刻を更新しない。この上限は終了通知の欠落そのものを検出するものではない。

- 初期入力待ち、正常な長時間シーン、Editor中の経過も上限に含む。
- 通常のポーズ中は判定する更新が止まるが実時間は進み、再開後に判定する。
- EditorやDebug復帰で更新が許可されている間は、ポーズ中にも上限を判定する。
- Startingだけの準備状態はこの30分上限の対象ではない。一致する終了、ロード、resetまで準備を維持する。
- 上限の変更、ポーズ時間の除外、準備・入力欠落専用の期限は現時点で追加しない。

### Editorと遅延通知

ゲーム時間の停止は通常のシーン進行を止めるが、すでに発生した外部通知を取り消さない。Editor中もシーン通知の採否表を適用する。一致する終了・resetは確認待ちより復帰を優先し、一致するChangeは1秒後の全候補再評価を予約する。期限に有効な入力を得られれば、Editor中でもこの一度の評価を行う。定期評価は引き続き停止する。

連続したEditor終了通知では復帰を重ねない。新しいEditorを開いた後にゲーム画面全体の終了通知が届いた場合は、その時点のEditorを閉じる。過去の編集開始に属する通知だけを除外する保証は持たない。

## 後続処理

アンカー以降の処理は、同じ手続きで次の順番に行う。

```text
アンカー
  -> プリセット候補
  -> raycast・clearance評価
  -> 有効候補の選択
  -> カメラpose
  -> Runtimeへの出力
```

各段階の計算はCoreの独立した機能とし、手続き側は入力と結果を次段へ渡すだけにする。
