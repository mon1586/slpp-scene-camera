# スレッド設計

## 目的と前提

通知元の実行スレッドに依存せず、参加者収集、シーン状態の変更、カメラ制御、外部Modへの返却を、それぞれ必要な実行機会で進める。

SSC専用・TDM専用という名前だけで実行スレッドを区別しない。通常の関数呼出しは呼出元と同じスレッドで実行され、別DLLのAPIを呼んでも自動的には移動しない。処理を登録した時点と、登録された処理が後で実行される時点は別であり、両者のスレッドが同じであることは前提にしない。

本設計では、ゲームのメイン更新と対応カメラ更新が同じメインスレッドで順に実行されることを実行条件とする。ただし両者は別の実行機会であり、カメラ更新が停止してもメイン更新は利用し得る。この条件と各外部APIの実行条件は、対象ランタイムごとに確認する。

## 実行機会と責務

| 実行機会 | 担当する処理 | 境界 |
| --- | --- | --- |
| 初期化 | 外部連携を準備する | 初期化時のスレッドを、その後の通知処理のスレッドとみなさない |
| シーン通知の到着 | 入力を検証し、後で処理する通知として受け付ける | 参加者収集とシーン状態の変更は行わない |
| ゲームのメイン更新 | 通知の順次処理、参加者収集、シーン状態の遷移、返却待ちの再試行 | 通常の構図反映は行わない |
| 対応するカメラ更新 | 身体中心の取得、構図の評価・追従・反映、開始時のTDM解除要求・確認 | 外部APIの実行条件と所有権を満たした場合に操作する |
| 終了・ロード・resetの到着 | 終了要求を受け付け、必要な保留通知を無効にする | 到着元のスレッドで返却完了を保証しない |
| 入力・Editor・描画 | 操作要求を渡し、表示用の結果を受け取る | UIからシーン状態・カメラ所有権・構図を直接変更しない |

終了処理はメイン更新でも対応カメラ更新でも進められる。返却に失敗した場合は義務を保持し、メイン更新が続く限り再試行する。カメラ更新の再開や追加のシーン通知を待つことを条件にしない。

## 状態の所有と受け渡し

- 参加者、シーンの進行状態、アンカー、評価結果、選択中の構図は、メイン更新と対応カメラ更新の実行領域で管理する。通知元から変更しない。
- 通知・操作要求を受け付けたことと、それがゲームへ適用されたことを区別する。UIは適用結果を受け取って表示する。
- 異なる実行領域へ渡す要求や表示結果は、受取側が一貫した内容として参照できること。使用中の結果が送信側の変更で書き換わらないこと。
- シーン通知は受け付けた順に処理する。同時に到着した通知間の順序は、受付順が決まる前には保証しない。
- 通知処理中に新しく届いた通知は次回以降のメイン更新で扱い、同じ実行機会の処理を無期限に延長しない。
- ロード前に受け付けた保留通知は、ロード後の参加者収集・シーン処理へ進めない。ロード後に初めて届く過去シーンの通知の識別限界は[Runtime仕様](runtime-spec.md)に従う。

## 開始と解除の時系列

以下は処理の前後関係を示す。各行が別フレームになることや、一フレーム内のメイン更新とカメラ更新の固定順序を表すものではない。

```text
通知元のスレッド                 ゲームのメインスレッド
       |                                    |
  開始通知を受け付ける                      |
       |---------- 通知の受け渡し ---------->|
       |                             [メイン更新]
       |                              参加者を収集
       |                              開始を受理
       |                              解除・初期評価を予約
       |                                    |
       |                             [対応カメラ更新]
       |                              TDMへ解除要求
       |                                    |
       |                             [TDMの更新]
       |                              ロックオンを解除
       |                                    |
       |                             [後続の対応カメラ更新]
       |                              解除を確認し禁止を返却
       |                              初期構図を決定
```

TDMが利用できない、ロックオンしていない、または要求が拒否された場合は解除待ちを作らない。受理後の待機上限や取消条件は[シーンカメラ手続き](scene-camera-procedure.md)と[Runtime仕様](runtime-spec.md)に従う。

## 更新停止時の返却

```text
対応カメラ更新が停止
       |
終了・reset要求を受け付ける
       |
ゲームのメイン更新 -> 通常のシーン処理を終了 -> 返却を試みる
       |                                      |
       |                                  失敗なら保留
       v                                      |
次のメイン更新 <-------------------------------+
       |
返却成功 -> 待機状態へ戻る -> 同じ所有権を再度返却しない
```

ポーズ中も返却処理を進める。ゲームのメイン更新そのものが停止している期間は完了時刻を保証せず、実行機会の再開後に保留処理を進める。実行機会を失ったことを、返却成功として扱わない。

## 外部APIの実行条件

- APIを呼ぶ場所の実行スレッドと、APIが要求するスレッドを確認する。スレッドIDは照合のための情報であり、処理の転送先を指定するものではない。
- 不一致の場合は要求されたゲーム状態変更を実行せず、理由を記録する。取得済みの所有権の返却は保留として残す。
- 所有権の取得、要求の受理、状態変化の確認、所有権の返却を区別する。他Modの所有権を奪わない。
- TDMの初回解除後にユーザーが再ロックした場合は、その操作を継続的に取り消さない。

## 確認項目と証拠の範囲

| 条件 | 期待する結果 |
| --- | --- |
| ワーカーから開始通知が到着 | その場では参加者収集・シーン状態変更を行わず、メイン更新で実行する |
| 通知の処理中に次の通知が到着 | 既存の受付順を保ち、新しい通知は次回以降に処理する |
| 開始通知を保留したままロード | 古い通知の参加者収集・シーン開始を行わない |
| カメラ更新が停止した状態で終了 | メイン更新だけで返却を進める |
| 返却に一度失敗 | 次のメイン更新で再試行し、成功後は二重返却しない |
| ポーズ中に終了 | 通常の追従を止めたまま返却を進める |
| 外部APIのスレッド条件が不一致 | 状態変更を実行せず、必要な返却義務を保持する |
| ゲーム起動ごとにスレッドIDが変わる | 固定した数値に依存せず、その起動時の実行条件を確認する |

単体テストは通知の受け渡し、処理順序、返却の再試行を検証する。実際のメイン更新とカメラ更新のスレッド一致、ポーズ・対象外カメラでの実行機会、外部Modとの共存は実ゲームで確認する。

異なるスレッドIDを観測しただけでは、処理の同時実行やデータ競合が起きたとは断定しない。逆に通常動作が成功しただけで、すべての共有状態の安全性が証明されたとも扱わない。入力・描画を含む各外部実行機会の同期条件は、確認済みの範囲と未確認の範囲を分けて記録する。

実装の接続位置・同期手段・調査証跡は[追加調査記録](spec-investigation.md)に記載する。
