# アニメーションフィルタ実装計画

これは実装作業用の計画であり、製品の振る舞いは[設計仕様](animation-filter-design.md)を正とする。実装と自動テストは完了し、実機受入確認を残している。

## 責務

- SexLabPSceneSource: 通知の検証と受信。StageStartを対象に加える。
- CameraHook / MainUpdateDispatcher: 通知・取得完了をメイン更新へ渡す。
- AnimationUpdateCoordinator（新設）: シーンの生存期間、更新番号、取得待ち、期限、確定を管理する。
- AnimationMetadataStore（新設）: 確定したID・名前・タグまたは情報不明を保持するだけ。独自通知・監視を持たない。
- PresetFilterEvaluator（新設）: 正規表現の検証・照合。
- SceneCamera: 確定情報と最新プリセットに基づく候補評価、選択保留、選択再開。

## 受信と確定の競合対策

イベントをメインキューへ積むだけでは不足する。既存Dispatcherは取り出したバッチを処理するため、バッチ取り出し後の新通知を見ずに旧応答で確定し得る。

対象通知の受信時に、メインキュー投入より先に受信番号を更新する。シーン終了とロードも同じ無効化境界に含める。シーンkeyだけでなくローカルの生存期間番号を使用する。取得要求は生存期間・受信番号・要求番号を保持する。

受信番号の更新と、候補の最終公開・通常選択は同じ短い排他区間で順序を確定する。単にatomicを一度確認してから公開する方式にしない。対象外の通知で現在シーンを無効化しない。ロック内でVM呼び出し、LOS、正規表現、ファイルI/O、カメラAPI呼び出しを行わない。重い計算は外で行い、公開時に生存期間・受信番号・プリセットrevision・移動状態を再検証する。検証失敗なら公開せず、最新状態の評価へ回す。

入力処理も同じ有効性を確認し、未処理の新通知がある間は古い候補で選択しない。これはSSC内での選択決定の順序保証であり、SLP+の変更をロックするものではない。

## 取得と保留

AnimationStartingは準備・保留、AnimationChangeは旧要求を無効化して開始通知待ちにする。AnimationStartとStageStartは新しい更新としてIDを非同期取得する。後続通知が来たら旧要求を打ち切り扱いにする。同じIDなら確認済みの名前・タグを再利用し、違うIDまたは未取得なら両方を取得する。

VMコールバックは要求専用の応答領域へ値を格納するだけとし、ストアやSceneCameraを直接変更しない。ID・名前・タグが揃った後、Coordinatorがメイン更新で評価を進める。ストアと候補は共通の更新番号で公開し、最後に選択保留を解除する。ストア単独の更新通知は設けない。

期限切れ・失敗も同じ確定経路を通し、情報不明と条件なし候補を公開する。打ち切った要求はその後成功しても採用しない。連続通知時は未着手要求を最新へ集約し、VM呼び出し数に上限を設け、上限超過を取得失敗として扱う。毎フレームの完了・期限確認は行うが、毎フレームのメタデータ要求は行わない。

StageStartはローカルPSCのResetSceneでSetActiveSceneより後に送られる。ただし全経路の保証ではなく、実機でUI変更とキー変更を確認する。Changeが却下されてStageStartが来ないケースは期限切れへ進める。

## 作業順

1. 設計仕様に沿ってCoordinator、保持情報、選択保留と受信境界を追加する。
2. regex編集・保存・候補評価を一体で追加する。保存形式の詳細は変更前に保存形式の設計文書へ反映する。
3. AnimationMetadataProbe / AnimationMetadataCapture、CameraHookの計測呼び出し、専用計測テストとCMake登録を削除する。調査ログと調査結果は残す。
4. 設計の順序逆転・終了・同一key再利用・期限切れ・編集競合を、制御可能な時計と応答順序でテストする。受信と公開の間へ通知を差し込むケースも検証する。
5. build.cmdでビルド・既存テストを実行し、UI変更、キー変更、通常ステージ進行、移動、連続変更、終了を実機で受入確認する。
